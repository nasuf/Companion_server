# AI 送礼流程（神秘礼物 + 用户签收 + 后台手动寄送）

> 2026-10-15。代码入口：`app/services/offline/gift_status.py`（状态机与可见性单一来源）、
> `gift_service.py`（用户侧 + 自动送礼）、`gift_admin_service.py`（后台手动寄送）、
> `gift_recommendation.py`（后台推荐分析）。

## 1. 状态机

```
pending_address → selecting → ordered → shipping → out_for_delivery → delivered
                                  └────────── failed / skipped / cancelled
```

| 状态 | 含义 | 谁推进 |
|---|---|---|
| `ordered` | 已下单，待发货 | 自动送礼下单 / 后台寄送 |
| `shipping` | 运输中（`packed` 揽收节点也归入此状态） | 物流同步 / 后台录入 |
| `out_for_delivery` | 派送中，**用户可以签收** | 物流同步（含快递侧「已送达/驿站代收」）/ 后台录入 |
| `delivered` | **已签收 = 已收到**，礼物揭晓 | 只能由用户点「确认签收」，或后台「代用户确认签收」 |
| `cancelled` | 后台撤销 | 后台 |

要点：

- 快递侧的「已送达」不等于签收，只推进到 `out_for_delivery`；轨迹表里 `status='delivered'`
  的节点只由签收动作写入。
- 进入派送中、签收两次迁移都是 SQL CAS（`mark_gift_out_for_delivery` / `mark_gift_received`），
  并发刷新、双击签收只生效一次，AI 消息也只发一次。
- 后台录入 / 删除物流节点后，礼物状态都按**时间最新**（按分钟比较，同一分钟以后录入的为准）的
  节点重新计算；补录更早的节点只补轨迹，状态不倒退；删掉误录的「派送中」会退回在途。
- 「有惊喜在路上」「派送中请签收」两类聊天通知每份礼物只发一次，以消息表里是否已有该通知为准
  （发送失败的会在下次迁移时补发）。
- provider 下单即报「已送达」也只记为在途，签收仍须用户确认。后台撤销后，进行中的自动下单流程
  不能再把礼物改回在途。

## 2. 签收前保密（神秘礼物）

在服务端脱敏，不依赖客户端隐藏（抓包、旧版 App 都看不到）：

| 出口 | 签收前 | 签收后 |
|---|---|---|
| `/offline/gifts*` 用户接口（`gift_status.user_view`） | 名称=「神秘礼物」，图片/寄语/原因/商品链接/价格为空，物流照常 | 全部可见；后台手动礼物的「送礼原因」始终不给用户 |
| 聊天礼物卡片（随消息永久落库） | 标题「神秘礼物」，无图片，`payload.revealed=false` | 签收时另发一张揭晓卡片 |
| AI 寄出提示 `offline.gift_sent_message` / 派送提醒 `offline.gift_out_for_delivery_message` | prompt 里**根本没有**礼物信息 | — |
| AI 签收揭晓 `offline.gift_received_message` | — | 带名称、原因、寄语 |
| 记忆 | 只写「寄出了一份神秘礼物，签收前保密」 | 写入礼物名 |
| 感谢 `/thanks` | 409（感谢消息会带礼物名） | 可用 |

## 3. 后台「礼物管理」（Web → 后台管理 → 礼物管理）

1. **按用户**搜索 → 用户概览：AI 伙伴、完整收货地址（可复制，用于寄快递）、充值/已送/剩余预算、画像标签。
2. **礼物推荐**：设预算 → 一次生成 5 个候选。每个候选列出依据的画像标签 `T#` / 记忆 `M#` 原文；
   编号由服务端核对，引用不存在的编号被丢弃，一个有效依据都没有的候选标「无可核对依据」。
   「不合适，换一批」会排除本轮看过的候选和已寄过的礼物。
3. **选定** → 带入**寄送礼物**表单：名称、图片（上传或链接）、随礼寄语（签收后展示）、送礼原因（内部）、
   实付金额（计入该用户礼物预算）、快递公司、运单号、当前进度。提交后用户收到神秘礼物卡片 + AI 消息。
   表单带 `request_id`（即礼物 id），重复提交不会寄两份；上次中途失败时，用同一提交重试会补齐
   轨迹与通知。
4. **礼物单 / 礼物记录 → 详情**：改信息/图片/快递、追加或删除物流节点（签收记录不可删）、
   代用户确认签收、撤销；「关联聊天消息」列出用户实际看到的每条消息并可打开 Trace。

手动礼物 `provider='manual'`：不调用任何下单 / 物流接口，轨迹全靠后台录入；不受系统设置里
「自动送礼」开关影响。上传的图片按收件用户存放（`/offline/media/{user_id}_...`），只有该用户和管理员可读。

## 4. 已知边界

- 自动送礼当前 provider 是 `mock`：开关开启时会给用户造出不会真实发货的在途礼物（3 天后进入派送中、
  可被签收）。在接入真实采购/物流前，建议关闭自动送礼，只走后台手动寄送。
- 旧版 App 没有签收按钮：礼物会停在派送中，需要后台「代用户确认签收」；旧版点「谢谢」会收到 409。
  一直没人签收的礼物会占着「当前礼物」名额，自动送礼不会再给这位用户触发（后台「待签收」列表可查）。
- 本次上线前已经发出的聊天卡片仍保留当时的礼物名（历史消息不回改）。
- 推荐批次的 Trace 只能复制 ID，后台暂无按 trace_id 直接打开的入口。
