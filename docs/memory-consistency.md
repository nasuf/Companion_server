# 三层记忆一致性与容量维护

2026-10-09 批次 MEMFIX-20261009。前台回复、意图提示词与检索预算保持原有配置。

## 计分与重放

聊天使用和夜间维护共用 `lifecycle/value.py` 的指数衰减与滞回阈值，半衰期保持 240 天。
夜间任务只做衰减，不从初始 `importance` 覆盖累积 `current_score`，不给访问奖励。
身份 singleton 保留 L1；每日总结不能由使用奖励晋升为永久核心人设。

使用事件以持久化的用户消息 ID、owner、workspace 校验；消息必须属于同一工作区的有效会话，
工作区仍处于 active 状态。事件接受期限 7 天；凭据保留 30 天后分批清理。
相同消息、同侧、同记忆只奖励一次，候选升级为实际注入只补足差额。
凭据、分数、层级和升降级审计在同一事务提交。数据库作用域锁和有序行锁避免丢失并发奖励；
singleton 的最终写入也使用同一作用域锁，避免与生命周期晋升同时造出第二条 L1。
使用更新失败会记录 warning 并回滚，前台回复继续；夜间失败会进入 cron 健康记录。

## 来源与日常总结

`profile_seed`、`knowledge_seed` 的可信身份、偏好、思维事实可在 L2/L3 保留精确分类。
AI 自述和日常总结不得据此创建新的永久人设。原来的 Web 提示词版本和内容不改动。

日常回顾使用配置时区中昨日 `[00:00, 次日00:00)` 的已保存作息、调整、主动消息与游戏记录，
同时限定 owner、agent、workspace。不会把今天 Redis 作息当成昨天的经历，也不会扫描别人的摘要。
总结只存生活与情绪，固定为 L3，importance 不超过 0.49。
每工作区每日数据库唯一凭据防止双 worker 重复生成，拆分后最多新增 5 条。
缺少昨日作息时不补造经历。

失败尝试标为 failed，并禁止自动重跑，避免部分写入后重复造记忆。
进程在提交状态前退出时会保留 running。运维应先核对该日期的实际写入与日志，
再决定是否人工修复；不得直接删除凭据盲目重跑。

## 容量边界与恢复

自动日常总结在每工作区最多保留 2,000 条原始条目，包含已归档条目；到达预算后记录
`capacity_skipped`，停止添加此类可选总结。正常聊天的事实、提醒和可信人设不受此预算限制。
摘要簇本身不再参与递归压缩；原文永久保留，实际用户历史仍需常规存储扩容与备份。

压缩摘要先以归档状态写入，随后在同一事务校验原文/归属、记录审计、归档全部原文并发布摘要。
中途失败不会留下部分归档或可用的重复摘要。
夜间每侧最多清理 500 条已归档 L3 原文向量，仅限有同作用域审计且仍有有效摘要的条目，
排除可信种子。原文和审计不删；这部分向量属于可以重新生成的派生数据。
归档未成功的未发布摘要及其向量会撤销；进程崩溃留下的同类临时输出在一天后分批清理。
这只删除从未生效、没有任何原文归档审计指向的派生摘要，不删除原始记忆。

撤销脚本 `scripts/undo_consolidation.py` 默认 dry-run。
真正撤销时先重建所有原文向量，再将向量、取消原文归档、归档摘要和撤销审计一起提交。
模型不可用、维度错误或任一数据库写入失败时保持旧状态。清理任务使用行锁跳过恢复中的条目。
重新生成向量依赖嵌入服务，因此服务不可用时可以看原文，但不能完成检索恢复。

## 有界夜间维护与发布

每侧一次最多选择 1,000 个最久未维护的 ID，按 owner/workspace 分组后每事务最多处理 250 条；
不加载全量 L2 内容或向量。活跃聊天即时更新，其余条目由最旧优先的兜底扫描逐批维护。
日志始终输出 user、ai 两侧完成计数和 `engine=cumulative_decay_v2`。
零候选是合法结果，不能据此推断任务没跑，也不能只看 Redis ok 就声称维护已验收。

两条新增 Prisma migration 只扩展凭据表、索引，并为缺少衰减时钟的历史行补上线时刻；
不修改原文、初始重要度、累积分数或层级，已有时钟不重置。历史 migration 不修改。
新表与旧应用兼容；回滚应用时保留这些表，禁止重置或回滚删除生产数据库。
旧应用会恢复旧的夜间计分方式，因此应用回退是临时故障恢复措施，应尽快恢复修复版本。

发布资格包括真实 PostgreSQL 并发/重放/回滚、总结隔离/日期/预算、压缩恢复/清理竞态、
5 万合成行的维护资源测试、迁移升级与旧 client 兼容、完整 CI 和真实容器聊天/worker 测试。
提交前必须完成两轮 review。发布后核对迁移、提示词指纹、worker、健康状态与错误日志。
自然 02:30 API 内调度验收继续单独记录，不能拿独立进程测试代替。

## 遗忘范围与历史重抽取语义

本节冻结当前语义（M02.04.01，M02.04.02 补齐 App 删除）。软归档和用户遗忘是两种不同的操作，只有后者会触发遗忘屏障。
用户遗忘可以是硬删除，也可以是保留文本的归档。

| 操作 | 入口 | 记忆行 | 向量 | 遗忘屏障 | 可撤销 |
| --- | --- | --- | --- | --- | --- |
| 用户遗忘（硬删除） | 聊天中“忘掉…”，`delete_memories_by_description` | 删除 | 删除 | 触发 | 聊天内撤销按快照重建为新 ID |
| App 批量删除 | `POST /memories/bulk-delete`，审计 `user_bulk_delete` | `is_archived=true` | 保留 | 触发 | 无用户入口，文本可人工恢复 |
| 工作区清空 | `wipe_workspace_memories`，审计 `workspace_wipe` | `is_archived=true` | 保留 | 触发 | 无用户入口，文本可人工恢复 |
| 压缩归档 | 夜间压缩，审计 `consolidated_into` | `is_archived=true` | 夜间可回收 | 不触发 | 运维脚本 `undo_consolidation.py` |
| 取消提醒 | 聊天取消提醒 | `is_archived=true` | 保留 | 不触发 | 撤回取消时恢复 |

遗忘屏障由数据库函数 `fence_forgotten_memories(side, workspace_id, ids)` 实现：递增工作区
`memory_erasure_epochs`，把证据来源消息写入 `memory_erased_sources`，将写入回执标为
`erased`，并把冻结抽取结果中相关事实替换为 `{"_erased": true}`。之后提交的抽取会按
这些记录拒绝被删除来源的内容。硬删除由 `BEFORE DELETE` 触发器调用它；App 批量删除和
工作区清空由 `archive_forgotten` 在归档、审计的同一事务中调用。压缩归档和取消提醒属于
内部归档，只让检索和上下文看不到该行，不登记来源。

### 源消息仍显示、但不得再次用于模型记忆的情形

- 用户遗忘某条记忆后（聊天删除、App 批量删除或工作区清空），源消息仍留在聊天记录里。其来源已登记在 `memory_erased_sources`，
  回执和冻结结果已脱敏。消息审计游标靠 `memory_extraction_sources` 反连接判定是否
  已处理，回执在删除后保留，所以这条消息不会被重新抽取。
- 抽取回执保留期间，任何已有回执的消息都不会被消息审计再次抽取；游标不早于该会话首个
  已登记批次的最早来源时间，不回填更早历史。
- 删除源消息时，未完成的批次标为 `blocked`、清空抽取结果，已提交的记忆按各自删除策略处理。

### 压缩撤销不会恢复已遗忘内容

`restore_consolidated_digest` 只在摘要仍为有效状态时执行。用户删除、批量删除或清空摘要
后撤销返回 0 条。已压缩原文本身已归档：App 批量删除跳过已归档行，聊天删除的向量检索
也排除已归档行，所以用户无法单独遗忘某条原文，撤销也不会把用户遗忘过的原文带回。
摘要被遗忘时，`fence_forgotten_memories` 沿 `consolidated_into` 递归找出压进它的原文，一并登记来源屏障、
删除向量并进入正文清理队列；原文行仍以归档状态保留，和 App 删除一致。

### 召回缓存与组装前校验（M02.04.04）

召回缓存键包含每个 (用户, 工作区) 的版本号，任何记忆写入、归档或遗忘都会递增它。
`hybrid_retrieve` 在召回开始前读一次版本，读缓存和写缓存都用这个版本。召回期间
发生遗忘时，结果写在旧版本下，之后的请求不会读到。

召回到组装之间还有回复前停顿和矛盾检测，所以缓存只是第一道防线。`prepare_reply`
在分级 prompt、主 prompt 和记忆使用登记之前调用 `keep_live_memories`：按库重查一次，
只保留仍存在、未归档、且属于当前用户和工作区的条目。查询失败时去掉所有带 ID 的条目，
本轮回复不带记忆。结果写入回复诊断 `memory_live_check`（status / checked / dropped）；status 为 checked、failed_closed、no_candidates（本轮没有召回）或 no_ids（只有旧格式条目）。
没有 ID 的旧格式缓存条目无法核对，原样保留，最多存活一个 5 分钟的缓存周期。

### 派生数据随来源失效（M02.04.03 部分）

| 派生数据 | 来源追溯 | 来源被遗忘后 |
| --- | --- | --- |
| 画像标签 `user_profile_tags` | `source_memory_ids` | 任一来源被删除或归档，读取时即不再返回该标签；下次画像刷新重建。无来源标签照旧返回 |
| 实体关系召回 | `memory_mentions` 关联记忆行 | 查询本就过滤已归档记忆，被删记忆的关联随行删除 |
| 用户画像文本 `user_portraits` | 无逐句来源 | 每周日 03:45 周更（近 7 天活跃的 agent）。用户遗忘（`delete` / `user_bulk_delete` / `workspace_wipe`）晚于最新画像时，每天 04:40 的 `portrait_forget_rebuild` 只按未归档记忆整份重建；已无 L1/L2 记忆时写入空版本。周更遇到遗忘也整份重建，变化段不含遗忘记录的原文 |
| 压缩摘要原文 | `consolidated_into` | 摘要被遗忘时原文一并遗忘：来源屏障、删除向量、清除 Trace 中的正文；归档行保留 |
| 使用回执 `memory_usage_receipts` | `memory_id` | 遗忘时随屏障删除 |
| 可见使用反馈 `memory_visible_use_events.payload` | 条目 `id` | 由正文清理任务把被遗忘条目的 text 换成 `[已遗忘]`；计数字段保留 |

画像周更以前会删除该工作区 7 天前的全部变更日志，其中包括 `consolidated_into`
等审计。生产上已有 8 条仍有效的压缩摘要因此失去撤销依据（只读核对，2026-11-18）。
周更现已不再删除变更日志；变更日志只由 `changelog_retention` 按 13 个月清理 `access` 行。

### 遗忘审计与日志不留正文（M02.04.05 部分）

用户遗忘（`delete` / `user_bulk_delete` / `workspace_wipe`）写入的变更日志只记操作、记忆 ID 和时间，
`old_value` 为空。聊天内撤销删除依赖 Redis 里 1 小时的快照，不读审计；App 删除的文本保留在归档行里。
删除与撤销的普通日志只输出 ID 和正文长度。此前写入的遗忘审计仍带正文（生产当前 0 行）。

### 遗忘后清除 Trace、镜像与待确认中的正文（M02.04.05）

遗忘屏障 `fence_forgotten_memories` 在删除或归档的同一事务里，把被遗忘记忆的正文复制进
`memory_forget_scrubs` 队列（随工作区级联删除）。每 5 分钟的 `memory_forget_scrub` 任务处理
入队满 10 分钟的行（让遗忘时正在进行的回合先写完 Trace），按工作区一次扫描：

| 位置 | 处理 |
|---|---|
| `messages.metadata`（`memory_retrievals` / `memory_retrieval_analysis` 等） | 按记忆 ID 把 text/content/summary 换成 `[已遗忘]`；其他字符串里的正文同样替换；比较交换写回，并发改动时下轮重试 |
| `trace_runs` inputs/outputs/extra/events | 正文替换为 `[已遗忘]` |
| `memory_visible_use_events.payload` | 按记忆 ID 替换 text |
| `message_traces` steps/summary/root_message | 同上 |
| Redis `deletion:pending:*` / `contradiction:pending:*` | 提到该记忆 ID 或正文的待确认票据直接删除 |

替换在解析后的 JSON 上做，不会截断转义序列。元数据里召回诊断带的正文（可能与当前正文不同的旧写法）
也一并纳入替换。全部成功后才删除队列行；失败累加 `attempts` 并记录异常类型，下轮重试。

边界：
- 少于 4 个字的正文只按 ID 清除，不在 Trace 全文里替换，避免误伤普通词（如“跑步”）。
- 正文在入队后最多保留约 15 分钟（延迟 10 分钟 + 5 分钟调度）；超过 1 小时未清理由数据不变量
  `forget_scrub_drained`（「遗忘正文清理」）判为 violated，只报条数和重试次数，不含正文。
- 聊天内撤销删除的 1 小时 Redis 快照是撤销功能本身，保留；源消息原文按 M02.04.01 语义仍显示。
- 运行任务载荷只带消息 ID（位置记忆）或建号人设参数（agent 初始化），不携带记忆正文，不做处理。
